*Visibility-graph + Dijkstra travel planning for material extrusion*

Reference implementation accompanying the paper Visibility-Graph Dijkstra Travel Planning for Stringing Reduction in Material Extrusion Printing (G. Donnici, M. Freddi, G. Galiè).

Given one sliced layer, the script computes the shortest travel move between two points that never crosses a hole and never leaves the printed region, and emits the G-code of that single travel move (retraction, G0 moves through the waypoints, un-retraction). The block is meant to be spliced into the G-code produced by an existing slicer, at the point where the slicer would otherwise issue a straight, possibly hole-crossing, travel move. This is a travel-planning module, not a slicer: it does not generate complete G-code.

How it works
A flat, triangulated STL (one layer) is read with trimesh.
The outer contour and the holes are recovered from the 2D union of all triangles (shapely.ops.unary_union) instead of the mesh edge-adjacency. This makes the extraction robust to overlapping or near-degenerate triangles (typical of fan triangulations around concave holes), which can corrupt boundary extraction based on edge adjacency.
Points are sampled on every contour (all mesh points are kept; a contour is decimated only if it exceeds 500 points) and a visibility graph is built: consecutive points on the same contour are always connected; any other pair is connected if the straight segment lies inside the outer contour and has zero-length intersection with every hole. Edge weights are Euclidean distances.
Dijkstra's algorithm finds the shortest path between the start and the goal node.
The script prints the path and the travel G-code block and saves a PNG of the result.

Installation
Python 3.8 or newer.

bash
python -m pip install -r requirements.txt
Usage
bash
python dijkstra_gcode_planner.py path/to/layer.stl

Without arguments the script looks for layer_piatto.stl in the same folder as the script.

Input: a flat, triangulated STL of a single layer (only the x and y coordinates are used), for example exported from Blender.

Output:

console: number of graph nodes, direct start-goal distance, path (node names), length of the optimized travel, computation time, and the G-code block;
dijkstra_path_result.png next to the script: layer, sampled nodes and computed path.
Parameters
Start and goal. By default the lexicographically smallest and largest outer-contour nodes (bottom-left and top-right corner of a square layer). Change them in main() to plan between any two nodes of the graph.
max_points_per_contour (default 500), argument of graph_from_flat_layer_mesh(): contours with more points are decimated at a fixed stride to bound the number of tested pairs.
G-code block. path_to_gcode(path_coords, feedrate_travel=6000, retract_mm=0.6, retract_feedrate=2400); feedrates are in mm/min. Set them to match the retraction and travel settings of your slicer profile.
Computation time. The reported time runs from STL loading (including library import) to the end of the Dijkstra search; plotting is excluded.
Limitations
One layer at a time. For a 3D part, slice the mesh at each Z and process each layer independently; this is not automated here.
One outer contour plus holes. If the triangle union has several disconnected regions, only the largest one is used.
The visibility graph tests every pair of sampled points, so the cost grows quickly with the number of nodes.
The path may touch hole boundaries (zero clearance); no safety margin for nozzle or line width is applied.
Optimality refers to the polygon defined by the sampled contours, not to the toolpath actually generated by the slicer.
